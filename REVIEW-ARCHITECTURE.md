# Архітектурне ревʼю: придатність до розширення

Дата: 2026-10-07, гілка `fumadocs`, коміт 775d134. Код прочитано повністю (~4200 рядків `src/` + `scripts/`), `npm run check` зелений (114 юніт-тестів), 52 e2e у списку. Файли не змінювались.

## Вердикт

**Архітектура міцна і для розміру проєкту навіть «на виріст» — це правильно, бо проєкт розрахований на супровід через Claude Code, де механічні перевірки замінюють людське ревʼю.** Головні рішення (три рівні з лінт-межами, чистий `model/` з reducer, реєстр типів завдань, рендер формул під час збирання, один конвеєр Markdown, контент як дані з перевіркою схемою) — правильні і взаємно узгоджені.

Оцінка за сценаріями розширення (скільки файлів треба торкнутись і чи попередить система про пропуск):

| Сценарій                             | Файлів            | Страхує                                 | Оцінка         |
| ------------------------------------ | ----------------- | --------------------------------------- | -------------- |
| Нова тема / розділ                   | 0 коду            | `check`, e2e підхоплюють самі           | відмінно       |
| Нова практика                        | 0 коду            | схема, lint, `math-checker`, e2e        | відмінно       |
| Нова схема для теорії                | 3–4 + e2e         | реєстр MDX; e2e пишеться руками         | добре          |
| Зміна формату іспиту (літери, склад) | 1–2               | `exam.ts`; `% 5` в e2e — руками         | добре          |
| Дві відповіді в `short`              | 1–2               | у межах модуля `short` + тип в e2e      | добре          |
| **Новий тип завдання**               | **~9**            | TypeScript страхує лише 3 з них         | посередньо     |
| **Сторінка прогресу**                | нова маршрутка    | `ProgressStore` не вміє перелічити теми | посередньо     |
| **Змішаний тест з кількох тем**      | помітна переробка | теги й `id` завдань локальні для теми   | складно        |
| Параметричні (генеровані) завдання   | зміна моделі      | суперечить рендеру під час збирання     | не передбачено |

Далі — що саме заважає в «посередньо» і «складно», і де задекларовані правила не збігаються з тим, що перевіряється.

## 1. Розбіжності між задекларованим і перевіреним

Це найважливіше для проєкту, який супроводжує агент: він довіряє AGENTS.md, а правило без перевірки з часом порушується.

**1.1. Межі для `scripts/` не перевіряються.** AGENTS.md, п. 8: «`scripts/` імпортує лише `model` і `lib`». У `eslint.config.mjs` блок `boundaries` має `files: ["src/**/*.{ts,tsx}"]`, тож елемент `scripts` і його політики ніколи не спрацьовують. Перевірено: файл у `scripts/`, що імпортує `trainer/components/trainer-card`, проходить лінт без зауважень. Виправлення — додати `scripts/**/*.ts` у `files` того блоку.

**1.2. `model/` може імпортувати Fumadocs.** AGENTS.md, п. 3: «`next/*` і `fumadocs-*` знають лише `app` і `content`». Заборона для `model` покриває лише `react`, `react-dom`, `next`; заборона Fumadocs — лише для `components`/`hooks`. Перевірено: `trainer/model` з `import { loader } from "fumadocs-core/source"` проходить. До того ж `shared/lib/i18n.ts` імпортує тип з `fumadocs-ui/i18n` — це виправдано, але суперечить формулюванню правила; варто або винести `i18n.ts` у `content`, або уточнити правило.

**1.3. «Єдине місце розгалуження за типом — `answer-field.tsx`»** (`.claude/rules/trainer.md`) — неточно. `trainer-card.tsx` знає тип `choice` (клавіша-цифра обирає варіант), `schema.ts` знає `match` і `short` поіменно (ліміти складу), `e2e/content.ts` і `e2e/trainer.spec.ts` знають усі три. Див. п. 2.

## 2. Новий тип завдання — реальна вартість

Задекларовано 4 кроки (модуль, реєстр, компонент, гілка в `answer-field`). Насправді потрібно ще:

- `model/schema.ts` — ліміти складу перелічені вручну (`inRange("тип match", …)`, `inRange("тип short", …)`), хоча `EXAM.composition.types` — обʼєкт, який можна обійти циклом;
- `model/exam.ts` — ліміт для нового типу;
- `components/trainer-card.tsx` — клавіатура: цифра працює лише для `choice`; для типу з варіантами (напр. «кілька правильних») треба нова гілка. Логічне місце — метод у `QuestionModule` (напр. `onDigit`), а не картка;
- `e2e/content.ts` (`PracticeQuestion`), `e2e/trainer.spec.ts` (`answerCorrectly`/`answerWrongly`) — e2e самі знають, як відповісти на кожен тип. Альтернатива — методи `correctDraft`/`wrongDraft` у модулі типу й один юніт-тест, що проганяє кожну практику через reducer (див. п. 5);
- `scripts/print-rules.ts`, `.claude/skills/practice/reference.md`, README «Типи завдань».

Висновок: реєстр спроєктований добре, але **контракт `QuestionModule` неповний** — знання про тип витікає в картку, схему складу й e2e. Три доповнення контракту (ліміт складу з обʼєкта, клавіатура, еталонні чернетки) зроблять «новий тип = один модуль + один компонент» правдою.

## 3. Угода «тема = глибина 2» записана в пʼяти місцях

`content/<розділ>/<тема>/index.mdx` і `practice.mdx` поруч — гарна угода, але її знають незалежно:

- `content/model/topic.ts` — `slugs.length` 2..3;
- `content/model/frontmatter.ts` — regex `practice\.mdx$`;
- `content/model/page-tree.ts` — `url.endsWith("/practice")`;
- `scripts/check-content.ts` — `file.split(/[\\/]/).length === 4`, `parts.length === 3`;
- `e2e/content.ts` — regex за шляхом файлу.

Поки структура плоска — працює. Поява вкладених розділів («Алгебра → Рівняння → Лінійні») зламає все одразу, і лінт цього не побачить. Пропозиція: `topic.ts` стає єдиним джерелом угоди (функції «тема за шляхом файлу», «тема за slugs», «чи практика»), а `check-content` та `e2e/content.ts` імпортують його (для e2e потрібен дозвіл імпорту з `content/model`; це чиста функція без Next).

## 4. Прогрес і теги — локальні для теми

- `tags` — ключі на кшталт `classify`, `sets`; гарантії унікальності між темами немає, і вона не потрібна, доки результати дивляться в межах теми. Для змішаного тесту чи сторінки «слабкі правила» потрібен складений ключ `<slug>/<tag>` — краще закласти зараз у `TrainerResult`/`Progress` (версія 3 з міграцією вже передбачена).
- `id` завдання — індекс у frontmatter теми; глобального ідентифікатора немає.
- `ProgressStore` має `load(id)` і `save`, але не `list()`. Сторінка прогресу зможе перебрати slug з `source` і викликати `load` по кожному — працює, але сховище не знає, що в ньому є; після перейменування теми записи стають «сиротами» без можливості їх знайти.
- Накопичені `tags` не мають часу: «правильно 3 з 10 за весь час» не відрізняє торішні помилки від учорашніх. Для сторінки прогресу знадобиться або вікно останніх N проходів, або позначки часу.

Усе це локалізовано в `progress.ts` і `session.ts`, що чисті й покриті тестами — переробка дешева, якщо зробити її до появи великої кількості збережених даних.

## 5. Масштабування перевірок під контент

`verify` = `check` + knip + format + **build + e2e** і є частиною Definition of Done. e2e генеруються з контенту: кожна сторінка → 2 тести × 2 пристрої, кожна практика → повне проходження × 2 пристрої. Зараз 52 тести на 5 сторінок і 1 практику. При 40 темах з практиками — близько 400 тестів, із них 80 повних проходжень по 10–15 завдань у реальному браузері. Це хвилини на кожне «завершення роботи» і головний практичний гальмівник етапу 4.

Варіант, який архітектура вже дозволяє: модель чиста, тож «кожна практика проходиться до кінця з правильними відповідями» можна перевірити у Vitest за секунди — прочитати всі `practice.mdx`, прогнати через `trainerSchema` + `renderTrainer`, зімітувати сесію через `sessionReducer`. Для цього модулю типу потрібна «еталонна чернетка» (п. 2). У e2e тоді лишається по одному сценарію на тип завдання плюс поведінка сторінок — незалежно від кількості тем. У CI можна залишити повний прогін.

Також `check-content.ts` тримає **власну копію конвеєра** (remark-parse + mdx + gfm + math + rehype-katex), а не `createMarkdown`, бо йому потрібні `remark-mdx` і всі помилки одразу. Це друге джерело правди для списку плагінів: новий remark-плагін у `markdown.ts` не потрапить у `check`. Варіант — `markdown.ts` експортує базовий список плагінів, а `check-content` додає до нього `remark-mdx`.

## 6. Свідомі обмеження, які варто зафіксувати письмово

Це не недоліки, а межі, у яких рішення оптимальне. Їх немає в README «Нюанси та обмеження», і при постановці задач «на виріст» вони здивують.

- **Завдання лише статичні.** Увесь текст рендериться в HTML під час збирання, KaTeX у браузер не їде. Генеровані завдання з випадковими числами потребують або KaTeX у клієнті, або рендеру на сервері під час запиту — тобто іншої моделі. Якщо генератори колись знадобляться, це окреме рішення, а не доповнення.
- **Рисунок до завдання — статична картинка, вбудована base64.** Інтерактивна фігура (Mafs) у завданні неможлива, бо `figureHtml` — рядок. Для теорії Mafs ляже у `diagram` без проблем.
- **Прогрес — лише localStorage цього браузера.** Зафіксовано в README. Інтерфейс `ProgressStore` дозволяє замінити сховище, але синхронізація потребуватиме бекенду, якого в проєкті немає.
- **Тренажер монтується лише після гідрації.** На практиці видно «Завантаження тренажера…» без JS. Для особистого сайту прийнятно.
- **Інтерфейс — лише українською, рядки в коді.** Правильно для проєкту; не варто вводити i18n-фреймворк.

## 7. Дрібне

- `exam.ts` змішує профіль іспиту (літери, склад) з ідентичністю сайту (`siteTitle`, `siteDescription`, `titleTemplate`); `app/layout.tsx` імпортує назву сайту з `trainer/model`. Назва сайту належить `app` або окремому конфігу — інакше поява другого профілю (ДПА, інший предмет) торкнеться тренажера.
- `diagram` — «усі схеми в одних сегментах»: правильно для 5–10 схем; при 20+ схем зі своїми моделями й хуками папки стануть плоскими списками. Тоді — підпапки за схемою всередині сегментів (як `trainer/model/question/`), конфіг лінта це вже дозволяє.
- `check-content.ts` — 300 рядків з усіма перевірками в одному файлі (frontmatter, формули, структура теорії, словник, `meta.json`). Список правил контенту росте швидше за код — варто перейти до реєстру правил, як у `trainer/model/lint.ts`, щоб нове правило було одним записом.
- Документація одного факту живе в 4–5 місцях (AGENTS.md, README, `.claude/rules`, skills, `reference.md`). Склад тренажера вже генерується (`npm run rules`) — це правильний напрямок; для типів завдань і правил контенту можна зробити так само.
- Залишки з ревʼю 7 жовтня актуальні: F16–F18 (пошук), F20 (перша формула у збиранні), F24, F49 (tsc двічі у `verify`).

## Що робити, у порядку корисності

1. **Закрити прогалини enforcement** (п. 1.1, 1.2): `scripts/**` у `files` блоку boundaries; заборона `fumadocs-*` для `model`; уточнити правило про `i18n.ts`. Пів години, нуль ризику.
2. **Доповнити контракт `QuestionModule`** (п. 2): ліміти складу з циклу по `EXAM.composition.types`, клавіатура в модулі, еталонні чернетки для тестів. Тоді правило «новий тип — модуль + компонент» стане правдою, і це варто зробити до появи четвертого типу.
3. **Юніт-прогін усіх практик через reducer** і скорочення e2e до «по одному на тип» (п. 5) — до того, як практик стане десять.
4. **Централізувати угоду про шлях теми** в `topic.ts` (п. 3).
5. **Намітити формат прогресу v3** з глобальними ключами тегів і часом (п. 4) — перед сторінкою прогресу та змішаним тестом.
6. Зафіксувати межі з п. 6 у README «Нюанси та обмеження».

Пункти 1–3 закривають усе, що зараз реально заважає етапу 4; 4–6 — профілактика перед масштабуванням контенту.
