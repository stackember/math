# Підтримка проєкту через Claude Code

Мета: власник дає задачу одним рядком («/theory numbers/fractions — матеріал у material/fractions.md», «/practice fractions», «онови залежності») — Claude робить усе до перевіреного коміту. Усе, що можна перевірити машиною, перевіряє машина; усе, що треба пам'ятати, лежить у файлах, а не в голові моделі.

## 1. Принципи

1. **CLAUDE.md — карта, не підручник.** ≤ 150 рядків: словник, карта папок, команди, Definition of Done, посилання. Деталі — у `.claude/rules/*.md`, які підвантажуються лише для відповідних шляхів.
2. **Одна дія — один skill.** `/theory`, `/practice`, `/review-topic`. Skill = покрокова процедура + шаблон + чек-лист; правила складу — з коду (`!`-вставка), а не копія.
3. **Швидкий цикл.** `npm run check` (< 10 с: контент, типи, лінт, unit) — у кожній ітерації; `npm run verify` (збірка + e2e) — перед завершенням.
4. **Друга пара очей для математики.** Окремий агент `math-checker` зі свіжим контекстом перераховує кожну відповідь і приклад — автор своїх помилок не бачить.
5. **Hooks замість нагадувань:** форматування після правки, перевірка контенту після правки, заборона правити згенероване.
6. **Дозволи наперед** (`.claude/settings.json`): команди проєкту без підтверджень — власник не сидить біля кнопки «Дозволити».
7. **CI як страховка:** `verify` на кожен push; десктоп-застосунок показує статус.

## 3. Флоу

**Додати тему.** Власник: `/theory numbers/fractions` (+ матеріал у `material/fractions.md` або текстом). Claude: читає матеріал і сусідні теми → пише `content/numbers/fractions/index.mdx` за шаблоном (Коротко → Простими словами → Приклади → Пастки) → кожен приклад перераховує `python3` → вирішує, чи потрібна схема/рисунок (SVG у `figures/`, Mafs для графіка) → `meta.json` розділу → `npm run check` → перегляд у вбудованому браузері (світла/темна, телефон; скриншоти в підсумок) → `math-checker` → `npm run verify` → коміт → підсумок: що додано, що перевірено, що залишилось на розсуд власника.

**Додати практику.** Власник: `/practice fractions`. Claude: читає теорію → теги (3–6 правил) → план «тег × рівень × тип» за `RULES` → `practice.mdx` (блокові скаляри) → перерахунок відповідей скриптом → `check` → `math-checker` (незалежно) → перегляд кожного типу завдання в браузері → `verify` → коміт.

**Правка.** «У темі modulus приклад 3 неправильний» → Claude править, `check`, `math-checker` на файл, `verify`, коміт.

**Ревʼю.** `/review-topic fractions` → звіт: математика, відповідність формату, НМТ-подібність завдань, дублікати шаблонів, доступність — без змін у файлах.

**Регулярно.** Routine (хмарний розклад Claude Code) раз на тиждень: `npm outdated` → оновити minor/patch → `verify` → PR. TS 7 і ESLint 10 — не чіпати (блокери в CLAUDE.md).

## 4. CLAUDE.md — рекомендований зміст

1. Що це (2 речення) і словник: розділ, тема, теорія, практика, тренажер, завдання, правило (тег). «Урок», «питання» — не вживати.
2. Карта папок (10 рядків) — як у REVIEW-ARCHITECTURE.md §3.3.
3. Команди: `dev`, `check`, `verify`; коли яку.
4. Definition of Done: `verify` зелений; нові/змінені числа перераховано (`math-checker`); вигляд перевірено у браузері (скриншот у підсумку); AGENTS.md/README оновлено, якщо змінилась структура; коміт з описом українською.
5. Git-флоу (див. §9).
6. Жорсткі правила (5–7): мова; shadcn лише через CLI; залежності без `--force`; TS 7/ESLint 10 не ставити; не створювати файли «про запас».
7. Посилання на `.claude/rules/*`, README, цей набір звітів (поки актуальні).

Поточний AGENTS.md добрий за змістом; його розділи «Формули й MDX», «Формат теорії», «Схеми» переїжджають у `rules/content.md`, «Архітектурні рішення»/«Тести» тренажера — у `rules/trainer.md`, «Тести» — у `rules/tests.md`.

## 5. Skills

### Ревʼю `/practice` (поточний)

Добре: чіткі кроки, склад у таблиці, правила якості (хибні варіанти = типові помилки, без дублів шаблону), перерахунок відповідей, YAML-пастки описані, автоматичні тести.

Виправити:

1. Таблиця складу — копія `RULES` (F42). Замінити на динамічну вставку: `!`node scripts/print-rules.mjs`` — skill завжди показує актуальні числа.
2. Крок «`npm run build`» → `npm run check` (секунди замість хвилини); `build` лишається в `verify` наприкінці.
3. Правила YAML (reference.md) → блокові скаляри `>-`/`|` для `q`, `why`, тегів; одинарні лапки лише для масивів (F41).
4. Додати крок «`math-checker` незалежно перевіряє файл» перед `verify`.
5. Додати режим оновлення: «`/practice fractions` — додай 3 завдання на …» → skill розпізнає існуючий файл, дотримується складу, не ламає ключ прогресу.
6. Перегляд у браузері — через вбудований preview (`launch.json`): пройти по одному завданню кожного типу, скриншоти світла/темна/телефон у підсумок.
7. Прибрати правило «назва = назва теорії» (явний `title`), прибрати `<Trainer />` (рендер автоматичний).
8. У `description` коротше (ціль, тригери); `argument-hint: <slug теми>`.

### `/theory <розділ>/<slug>` (новий)

Кроки: вхідні дані (матеріал, сусідні теми, попередні/наступні за програмою) → план розділів → написати за `reference.md` (шаблон із прикладами callout-ів, таблиць, формул) → перерахунок прикладів → рішення про схему/рисунок за правилами з `rules/content.md` → `meta.json` → `check` → браузер → `math-checker` → `verify` → коміт. Чек-лист якості: кожне правило має приклад з розв'язком; «Пастки» — з типових помилок НМТ; без тестів у теорії; формули за правилами.

### `/review-topic <slug>` (новий, лише читання)

`disable-model-invocation: false`, `allowed-tools: Read, Grep, Glob, Bash(python3 *), Bash(npm run check*)`. Викликає `math-checker`, перевіряє формат і словник, оцінює завдання на НМТ-подібність і покриття «Пасток», повертає список «файл:рядок — проблема — як виправити».

Корисні поля frontmatter skill: `argument-hint`, `allowed-tools` (без зайвих підтверджень), `paths` (skill підвантажується автоматично, коли Claude працює з `content/**`), `context: fork` для `/review-topic`, щоб довгий звіт не засмічував основний контекст.

## 6. Агент `math-checker`

```md
---
name: math-checker
description: Незалежна перевірка математики у файлі теорії або практики: перераховує кожну відповідь, приклад і твердження обчисленням (python3, fractions, sympy), шукає неоднозначні умови, хибні пояснення й варіанти, що залежать від порядку. Викликати після написання або зміни контенту.
tools: Read, Grep, Glob, Bash
---

Отримуєш шлях до файлу. Для кожного числового твердження напиши обчислення (python3) і порівняй.
Для кожного завдання: чи правильна відповідь єдина; чи хибні варіанти справді хибні; чи `why` пояснює саме це.
Повертай лише список: `файл:рядок — що не так — правильне значення`. Нічого не правиш.
```

Свіжий контекст — ключова властивість: агент не бачив міркувань автора і не повторює його помилку.

## 7. `settings.json`

```json
{
  "permissions": {
    "allow": [
      "Bash(npm run *)",
      "Bash(npm test*)",
      "Bash(npx playwright *)",
      "Bash(npx tsx *)",
      "Bash(npx shadcn@latest add *)",
      "Bash(python3 *)",
      "Bash(node *)",
      "Bash(git status*)",
      "Bash(git diff*)",
      "Bash(git log*)",
      "Bash(git add *)",
      "Bash(git commit *)"
    ],
    "deny": [
      "Edit(src/components/ui/**)",
      "Write(src/components/ui/**)",
      "Bash(npm install * --force*)",
      "Bash(npm install * --legacy-peer-deps*)",
      "Bash(git push --force*)"
    ]
  },
  "hooks": {
    "PostToolUse": [
      {
        "matcher": "Edit|Write",
        "hooks": [
          {
            "type": "command",
            "command": "node \"$CLAUDE_PROJECT_DIR/scripts/hooks/after-edit.mjs\""
          }
        ]
      }
    ]
  }
}
```

`after-edit.mjs` читає JSON події зі stdin: для `src/**`, `e2e/**`, `scripts/**` — `prettier --write <файл>`; для `content/**` — `check-content <файл>`; помилки друкує в stderr з кодом 2 — Claude бачить їх одразу, без збірки. `git push` лишається з підтвердженням.

## 8. `npm run check` і `scripts/check-content.ts`

`check` = `check:content && typecheck && lint && test` (≈ 5–10 с). `verify` = `check && format:check && build && test:e2e` (окремий `typecheck` у `verify` зайвий: `next build` сам ганяє tsc по всьому проєкту — F49).

`check-content.ts` (ті самі Zod-схеми й KaTeX, без Next, 1–3 с): frontmatter кожного файлу за схемою; рендер усіх текстів завдань (усі помилки формул одним списком); H2-розділи теорії у дозволеному наборі й порядку; `practice.mdx` лише поруч з `index.mdx`; slug тем унікальні; `meta.json` посилається на існуючі файли; іконки існують у lucide; словник («урок», «питання» у контенті); мінус `-` перед числом і десяткова крапка поза формулами, `|` у формулах таблиць. Вивід `файл:рядок: повідомлення` українською.

## 9. CI, хостинг, Git

- `.github/workflows/verify.yml`: Node 24, `npm ci`, `npx playwright install --with-deps chromium`, `npm run verify`, кеш npm і браузерів.
- Хостинг: Vercel (прев'ю на гілку, статус у десктоп-застосунку). Домен і аналітика — за бажанням.
- Git: **варіант А (рекомендований для одного власника)** — Claude комітить у `main` після зеленого `verify`, CI підтверджує; власник дивиться diff у панелі сесії. **Варіант Б** — гілка + PR на кожну задачу, власник мерджить після CI; більше кліків, але є місце для коментарів. Зафіксувати вибір у CLAUDE.md.

## 10. Специфіка Claude Code Desktop

- `launch.json` → вбудований браузер: skills зобов'язані перевіряти вигляд там і додавати скриншоти в підсумок (світла/темна, телефон).
- `/code-review` перед комітом великих змін; для рефакторингів — `/code-review ultra`.
- Routines (розклад у хмарі) — тижневе оновлення залежностей і `verify`.
- Worktree на сесію — паралельні задачі (теорія однієї теми і практика іншої) без конфліктів; `.worktreeinclude` не потрібен (немає `.env`).
- Автопам'ять — для вподобань власника; факти про проєкт — лише в CLAUDE.md/rules (щоб не розійшлися).

## 11. Код, який AI розуміє найкраще (правила для CLAUDE.md)

1. Маленькі модулі з JSDoc зверху: що, звідки викликається, інваріанти (як у `session.ts`).
2. Чисті функції + тести як специфікація; побічні ефекти — в одному місці.
3. Дискриміновані union-и й вичерпні `switch` замість паралельних типів і подвійних guard-ів.
4. Жодних неявних угод (`sets[0]` — домашня множина, «назва практики = назва теорії») — лише явні поля.
5. Перевірка на даних (mdast, Zod), а не на серіалізованому HTML регексами.
6. Одне джерело правди для чисел і правил (`RULES`); документи посилаються або генеруються.
7. Повідомлення помилок кажуть, що зробити, українською, з місцем.
8. Слухачі подій — у межах компонента, не на `window`.
9. Бібліотечний компонент замість власної ARIA-семантики.
10. Файл «про запас» не створюється; мертві експорти видаляються одразу (лінт `no-unused-exports` через `knip` — опційно).
