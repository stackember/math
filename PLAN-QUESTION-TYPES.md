# План: типи завдань як розширювана система + множинний вибір

Дата: 2026-10-07. Продовження [REVIEW-ARCHITECTURE.md](REVIEW-ARCHITECTURE.md), п. 2. Коду поки немає — лише план.

## Мета

Новий тип завдання = **два файли з логікою + по одному рядку у трьох реєстрах + приклад у документації**. Усе інше (reducer, картка, клавіатура, результати, схема складу, `check`, юніт-прогін практик, довідка для skill) не змінюється. Пропуск будь-якого кроку — помилка компіляції, а не тиха поломка.

| Що робить автор нового типу                    | Файл                                                | Хто страхує                           |
| ---------------------------------------------- | --------------------------------------------------- | ------------------------------------- |
| Схема, чернетка, перевірка, відповідь, клавіші | `src/features/trainer/model/question/<type>.ts`     | `defineQuestionType` вимагає всі поля |
| Поле відповіді на екрані                       | `src/features/trainer/components/<type>-answer.tsx` | тип пропсів з контракту               |
| Рядок у реєстрі моделей                        | `model/question/registry.ts`                        | `satisfies` по всіх типах             |
| Рядок у реєстрі компонентів                    | `components/answer-registry.tsx`                    | `satisfies Record<Type, …>`           |
| Рядок у реєстрі e2e-відповідачів               | `e2e/answers.ts`                                    | `satisfies Record<Type, …>`           |
| Рядок у README «Типи завдань»                  | `README.md`                                         | чек-лист у `.claude/rules/trainer.md` |

Критерій готовності етапу: множинний вибір додається саме так, і `git diff` не торкається `session.ts`, `trainer-card.tsx`, `schema.ts`, `lint.ts`, `print-rules.ts`, `check-content.ts`, `e2e/trainer.spec.ts`.

Контракт перевірено подумки на трьох кандидатах: `multi` (новий тип), `short` з двома полями (розширення наявного — лише його модуль і компонент), `order` «розстав за зростанням» (чернетка-перестановка, `displayOrder` перемішує — теж лягає без змін движка). Якщо контракт тримає всі три, він достатній.

## Етап A. Контракт модуля (model, без React)

Зараз `QuestionModule` знає рендер, порядок показу, чернетку, перевірку й відповідь. Знання, яке витекло назовні, повертаємо в модуль.

1. **`defineQuestionType({...})`** у `question/base.ts` — фабрика, що виводить `Q` зі схеми Zod і `D` з `emptyDraft`; модуль не пише дженерики руками і не може пропустити поле. Повертає модуль із полем `type` (літерал) і `schema`.
2. **`meta`** — `{ label: "вибір відповіді", answerHint: "клік по варіанту або цифра 1–5", example: "<YAML одного завдання>" }`. Джерело для повідомлення Zod `type: choice (…) або …` у реєстрі, для `npm run rules` (таблиця типів і приклади в skill) і для README.
3. **`digit?(question, order, digit)`** → оновлення чернетки або `null`. Картка тренажера перестає знати `choice`: натиснута цифра йде в модуль поточного завдання. Для `choice` — обрати, для `multi` — перемкнути, для `match`/`short` — відсутній.
4. **`correctDraft(question)` і `wrongDraft(question)`** — еталонні чернетки: правильна й гарантовано неправильна. Потрібні юніт-прогону всіх практик (етап C) і юніт-тестам самого модуля. Для `match` «неправильна» — зсув пар (як зараз в e2e), для `short` — `answer + 1`, для `multi` — доповнення множини.
5. **`lint?(question)`** → список `{ severity, text }` — евристики, що залежать від типу. Правило «варіант залежить від порядку» переїжджає у спільний помічник `positionalOptions(options)` у `base.ts`, яким користуються `choice` і `multi`; `lint.ts` лишає загальні правила і додає результат `moduleOf(q).lint?.(q)`. Нове правило для типу — у його модулі.
6. **`Draft` виводиться з реєстру** (`ReturnType<…["emptyDraft"]>` по кортежу модулів), а не перелічується руками. Реєстр: один кортеж модулів, з нього — `questionSchema`, `QUESTION_TYPES`, `Draft`, текст помилки для `type`.
7. **Склад тренажера — циклом.** `schema.ts` обходить `Object.entries(EXAM.composition.types)`; ключі перевіряються `satisfies Partial<Record<Question["type"], Range>>` у `schema.ts` (не в `exam.ts`, щоб не було циклу `exam ← choice ← registry`). Тип без запису — без обмежень; `choice` лишається «решта».

Поведінка трьох наявних типів не змінюється — це чистий рефакторинг, перевіряється наявними 114 тестами плюс нові тести на `digit`, `correctDraft`/`wrongDraft`.

## Етап B. Контракт компонента поля відповіді

1. **Єдина форма пропсів** `AnswerProps<Q, D> = { question: Q; draft: D; order: number[]; checked: boolean; correct: boolean; onAnswer(update: (draft: D) => D): void }`. `ShortAnswer` замість `value` отримує `draft`; `ChoiceAnswer` — `draft` замість `selected`. Обгортання в `updateDraft(type, …)` робить `AnswerField`, компоненти про нього не знають.
2. **`components/answer-registry.tsx`**: `{ choice: ChoiceAnswer, match: MatchAnswer, short: ShortAnswer } satisfies { [T in Type]: AnswerComponent<T> }` — TypeScript вимагає компонент для кожного типу з правильними пропсами.
3. **`AnswerField`** стає загальним: бере компонент з реєстру за `question.type`, звіряє `draft.type`, передає пропси. Єдине стирання типу — тут, дзеркально до `moduleOf`.
4. **`trainer-card.tsx`**: `onDigit` викликає `moduleOf(step.question).digit?.(…)`. Згадок `choice` у картці не лишається.
5. **`components/option-row.tsx`** — витягнути з `choice-answer.tsx` рядок варіанта (кружечок з літерою + текст + стилі за `Mark`), щоб `multi` виглядав так само, а не копіював класи. `Mark` уже має `missed` — для `multi` він потрібен.

## Етап C. Тести, що не ростуть із кількістю типів і тем

1. **Юніт-прогін усіх практик** (`src/features/content/model/practices.test.ts`, Vitest, секунди): прочитати кожен `practice.mdx`, пропустити через `frontmatterSchema` (та сама перевірка й рендер, що у збиранні), потім для кожного завдання через `sessionReducer`: `correctDraft` → `check` → `true`; `wrongDraft` → `false`; `invalidReason(correctDraft)` — `null`; `answerHtml` не кидає. Це доводить, що кожна практика проходиться й перевірка відповідей узгоджена з відповідями у файлі, без браузера. Новий тип потрапляє сюди автоматично.
2. **`e2e/answers.ts`** — реєстр «як відповісти в браузері» за типом: `{ correct(page, card, question), wrong(…) }`, `satisfies Record<Type, Answerer>`; тип `Question` імпортується з реєстру моделей лише як тип (`import type`, через `@/` — Playwright читає `paths` з tsconfig). Дубльований `PracticeQuestion` в `e2e/content.ts` зникає, `% 5` замінюється на `options.length` із frontmatter.
3. **Повне проходження кожної практики в e2e** лишається, але локально ганяється для **еталонного набору** — мінімальної множини практик, що разом покривають усі типи (обчислюється з frontmatter), а всі практики — лише в CI (`process.env.CI`). Так `verify` локально не ростиме з контентом, а CI перевірятиме все. Перевірки «сторінка відкривається без помилок» і «без горизонтальної прокрутки» дешеві — лишаються для всіх сторінок.
4. **По одному e2e-сценарію на тип** із його особливою поведінкою (для `multi` — перемикання варіанта, позначки «пропущено» після перевірки). Пишеться автором типу; `.claude/rules/tests.md` описує мінімум.
5. **Юніт-тести модуля** — обовʼязкові: схема відкидає неправильні дані з українським повідомленням, `isCorrect`, `answerHtml` при перемішаному порядку, `digit`, `correctDraft`/`wrongDraft`.

## Етап D. Документація й інструменти — з одного джерела

1. **`npm run rules`** друкує, крім складу, таблицю типів (`meta.label`, `meta.answerHint`) і YAML-приклад кожного типу (`meta.example`). Skill `/practice` уже вставляє його вивід через `!` — довідка про типи оновлюється сама. У `reference.md` лишаються правила YAML і формул, приклади типів з нього прибираються.
2. **`.claude/rules/trainer.md`**: розділ «Як додати тип завдання» переписується під новий рецепт (таблиця з «Мети») плюс чек-лист: README-рядок, e2e-сценарій, `exam.ts` якщо є ліміт складу.
3. **AGENTS.md**: структура (`answer-registry`, `option-row`, `e2e/answers.ts`) і рядок про юніт-прогін практик. README: розділ «Типи завдань» і «Перевірки якості».
4. **Прогалини лінта з ревʼю** закрити тим самим заходом, бо міняється `eslint.config.mjs`: `scripts/**` у `files` блоку boundaries; заборона `fumadocs-*` для `model`; `e2e/**` — дозволити лише `import type` з `src` (правило `@typescript-eslint/consistent-type-imports` або boundaries-елемент `e2e` з дозволом тільки на `model`).

## Етап E. Множинний вибір (`multi`)

Перший тип, що додається за новим рецептом, і водночас перевірка, що рецепт правдивий.

**Формат у frontmatter**

```yaml
- type: multi
  level: 2
  tag: irrational
  q: Які з чисел ірраціональні? Обери **всі** правильні варіанти.
  options: ['$\sqrt2$', '$\sqrt{16}$', '$\pi$', "$0{,}(3)$", '$\sqrt{20}$']
  answer: [0, 2, 4] # індекси правильних, з 0; від 2 до (кількість − 1), різні
  keepOrder: false
  why: "…"
```

**Схема** (`strictObject`, повідомлення українською): `options` — 3…5 рядків (`EXAM.letters.length` — верхня межа), різні; `answer` — унікальні індекси, відсортовані або сортуються при розборі, довжина від 2 до `options.length − 1` (одна правильна — це `choice`, усі правильні — беззмістовно); `keepOrder` як у `choice`.

**Модуль**

- чернетка `{ type: "multi", chosen: number[] }` (масив, щоб серіалізувалось);
- `isAnswered` — хоч один обраний; `invalidReason` — `null`;
- `isCorrect` — рівність множин, усе або нічого (як у НМТ для відповідності; часткового балу немає — `results: boolean[]` не міняємо);
- `displayOrder` — як `choice` (перемішує, якщо не `keepOrder`);
- `answerHtml` — літери правильних варіантів у порядку показу: «А, В, Д»;
- `digit` — перемикає варіант на позиції;
- `correctDraft` — `answer`; `wrongDraft` — доповнення `answer` до всіх індексів (непорожнє за схемою);
- `lint`: `positionalOptions` (спільний з `choice`) як `error`; `warn`, якщо умова не містить «усі»/«всі»/«які з» — учень має розуміти, що відповідей кілька;
- `meta`: label «кілька правильних відповідей», hint «клік або цифра перемикає варіант», приклад вище.

**Компонент `multi-answer.tsx`**: `CheckboxGroup` + `Checkbox.Root` з Base UI (shadcn: `npx shadcn@latest add checkbox`), рядки через `option-row.tsx`, `data-answer="multi"`, `data-option` — індекс із frontmatter. Позначки після перевірки: обрано і правильно — `correct`; не обрано, але правильно — `missed` (пунктир, як у відповідності); обрано, але неправильно — `wrong`. `readOnly` після перевірки, як у `choice`.

**Профіль іспиту**: `EXAM.composition.types.multi: [0, 2]` — у НМТ такого типу немає, тож тренажер не має ним заповнюватись; ліміт підбирається власником. У skill `/practice` — коли доречно: правило з кількома прикладами й контрприкладами («які з чисел ірраціональні», «які твердження правильні»), не більше 2 на практику.

**Тести**: юніт-тести модуля (п. C.5), один e2e-сценарій (перемкнути два варіанти, зняти один, перевірити з помилкою — побачити `missed` і `wrong`, цифрою перемкнути), рядок у `e2e/answers.ts`, юніт-прогін підхоплює сам. `math-checker` без змін — він читає `answer` як індекси.

**Контент**: 1–2 завдання `multi` у `number-sets/practice.mdx` як зразок (склад лишається в межах правил), перевірка `math-checker`.

## Далі за тим самим рецептом (поза цим планом)

- **`short` з двома відповідями** (формат НМТ, етап 4): `answer: number | [number, number]`, чернетка `{ values: string[] }`, два поля з `data-field`. Торкається лише `short.ts`, `short-answer.tsx`, рядка в `e2e/answers.ts` — підтвердження, що контракт тримає.
- **`order`** (розставити за зростанням) — за потреби; контракт готовий.

## Порядок роботи й коміти

1. **Рефакторинг контракту без нових типів** (A + B + C.1–C.3 + D.4): один коміт, `verify` зелений, поведінка сайту та сама. Це найбільший і найризикованіший крок; робити до `multi`, інакше новий тип доведеться писати двічі.
2. **Документація з одного джерела** (D.1–D.3): окремий коміт.
3. **`multi`** (E): окремий коміт — його diff і є доказом, що рецепт правдивий.

## Ризики й що свідомо не робимо

- **Рефакторинг зачіпає всі три типи й картку.** Страховка — наявні тести, e2e-проходження і новий юніт-прогін, який пишеться першим (C.1), ще до змін у компонентах.
- **Zod `discriminatedUnion` потребує кортежу схем** — реєстр лишається явним списком модулів (один рядок на тип), повної «автореєстрації» через файлову систему не робимо: вона ламає typecheck і knip.
- **Частковий бал за `multi`** не вводимо: змінив би `results`, прогрес, результати за правилами й вердикти. Усе або нічого — як у НМТ.
- **Генеровані завдання** — поза планом (див. ревʼю, п. 6).
- **Перетягування для `order`** — не зараз; якщо тип знадобиться, спершу кнопки «вгору/вниз».

| ---------------------------------- | ------------------------------------- |
| Кількість варіантів у `multi`      | 3–5 (літери А–Д)                      |

| Оцінювання `multi`                 | усе або нічого                        |

| Клавіша-цифра в `multi`            | перемикає варіант                     |
